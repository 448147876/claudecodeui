## 1. 项目背景与结构

**上游**：[siteboon/claudecodeui](https://github.com/siteboon/claudecodeui)（产品名 CloudCLI），一个给 Claude Code / Codex / Cursor CLI 用的网页界面：项目与会话管理、聊天、文件树与编辑器、git、网页终端、MCP/Skills 管理。单用户设计：一个进程、一个登录、看得到整个 home。

**本 fork**（`origin` = `448147876/claudecodeui`）在上游外面加了一层多账号网关：

```
浏览器 ──► cloudcli-multi 网关（127.0.0.1:3001）
             ├─ 登录 / 账号管理（/__gw/*），账号库 ~/.cloudcli-multi/gateway.db
             └─ 按账号转发 ──► 每个账号一个上游子进程（127.0.0.1:随机端口）
                                  admin：常驻，不隔离
                                  普通账号：按需启动、空闲 30 分钟回收，CLOUDCLI_ISOLATION_ROOT=账号目录
                                  全部共用一个 ~/.claude 登录
```

| 目录 | 归属 | 说明 |
|---|---|---|
| `src/` | 上游 | 前端（React + Vite），构建到 `dist/` |
| `server/` | 上游 + 少量补丁 | 后端（TypeScript），构建到 `dist-server/`；补丁只有 `server/shared/isolation.ts` 和 15 个调用点（见 04） |
| `gateway/` | 本 fork | 网关，纯 `.mjs`，不需要编译；`gateway/scripts/service.sh` 是本文的服务管理脚本 |
| `mydocs/` | 本 fork | 本目录 |
| `electron/`、`docker/`、`plugins/` | 上游 | 本部署不用 |

上游改动面很小、自己的代码都在独立目录，这是后面“改源码、合并上游都不容易互相破坏”的基础。

## 2. 安装形态（已完成）

不用 `npm install -g`（那会把代码复制一份到全局目录，改源码不生效、还要重复安装），而是**源码目录就是运行目录**，全局命令只是一个软链接：

| 组成 | 位置 | 说明 |
|---|---|---|
| 源码 / 运行目录 | `/home/vscode/tong/demo/claudecodeui` | git 仓库，`dist/`、`dist-server/` 是构建产物 |
| 全局命令 | `~/.local/bin/cloudcli-multi` → `gateway/scripts/service.sh` | 脚本按软链接反查源码目录 |
| Node.js | `~/.local/share/cloudcli-multi/node` → `node-v22.23.4-linux-x64` | **项目必须用 Node 22**：`node_modules` 中的原生模块（better-sqlite3、node-pty）按 Node 22 编译。系统自带的 `/usr/bin/node` 是 v18，跑不起来，但保留不动，不影响其他项目 |
| 配置 | `~/.config/cloudcli-multi/env`（600） | 启动时读取，改完 `restart` 生效 |
| 数据 | `~/.cloudcli-multi/`（700） | 账号库、各账号 `auth.db`、运行文件、备份、日志 |

`service.sh` 会固定用上面的 Node 22（可用 `CLOUDCLI_MULTI_NODE` 改），并把它放到 `PATH` 最前面，所以 `npm`、构建也都用 Node 22。

### 2.1 在新机器上重装

```bash
# 1. Node 22（用户目录，不需要 sudo）
D=~/.local/share/cloudcli-multi; mkdir -p $D
curl -fsSLO https://nodejs.org/dist/latest-v22.x/SHASUMS256.txt
F=$(grep -o 'node-v22[0-9.]*-linux-x64.tar.xz' SHASUMS256.txt | head -1)
curl -fsSLO https://nodejs.org/dist/latest-v22.x/$F && grep " $F\$" SHASUMS256.txt | sha256sum -c -
tar -xJf $F -C $D && ln -sfn ${F%.tar.xz} $D/node

# 2. 代码与依赖
git clone -b feat/multi-account https://github.com/448147876/claudecodeui.git && cd claudecodeui
PATH=$D/node/bin:$PATH npm ci

# 3. 全局命令 + 配置
ln -sfn "$PWD/gateway/scripts/service.sh" ~/.local/bin/cloudcli-multi
mkdir -p ~/.config/cloudcli-multi   # 写入 env，内容参考第 3 节

# 4. 构建并后台启动
cloudcli-multi update
```

## 3. 配置

`~/.config/cloudcli-multi/env`（`KEY=VALUE`，`#` 注释）：

| 变量 | 当前值 / 默认 | 说明 |
|---|---|---|
| `CLOUDCLI_MULTI_HOST` | `127.0.0.1` | 监听地址。保持回环地址，通过端口转发访问（第 5 节） |
| `CLOUDCLI_MULTI_PORT` | `3001` | 网关端口 |
| `CLOUDCLI_MULTI_HOME` | `~/.cloudcli-multi` | 数据目录 |
| `CLOUDCLI_MULTI_WORKSPACES` | `~/workspaces` | 新建账号时默认工作目录的父目录 |
| `CLOUDCLI_MULTI_IDLE_MINUTES` | `30` | 普通账号空闲回收阈值 |
| `CLOUDCLI_MULTI_TRUST_PROXY` | `false` | 放在 HTTPS 反向代理后面时设为 `true` |
| `CLOUDCLI_FILE_TREE_MAX_ENTRIES` | **`50000`**（上游默认 10000） | 文件树上限，见下 |

其余变量见 03 第 9 节。

### 3.1 文件树上限与响应压缩（2026-10-25）

上游打开「文件」时一次递归读取整个项目（最多 10 层），超过上限直接报错 `Project file tree exceeds the 10,000 entry limit`、一个文件都不显示。⌘K 文件搜索、聊天 `@` 引用也用同一份完整列表。实测开销（每条约 250 字节 JSON）：

| 条目数 | JSON | gzip 后 | 服务端读取 | 服务端内存 |
|---|---|---|---|---|
| 1 万 | 2.4 MB | 153 KB | 约 0.1 秒 | 约 27 MB |
| 2 万（tong 根目录） | 4.7 MB | 320 KB | 约 0.15 秒 | 约 46 MB |
| 5 万（当前上限） | 约 12 MB | 约 750 KB | 约 0.35 秒 | 约 75 MB |
| 10 万 | 23.9 MB | 1.5 MB | 约 0.7 秒 | 约 150 MB |

- **上限**：改为 5 万（`CLOUDCLI_FILE_TREE_MAX_ENTRIES`，上游补丁 16）。不够时可调到 10 万，`restart` 生效，不用改代码；再大建议按子项目打开。
- **压缩**：网关对 JSON/JS/CSS/HTML/SVG/文本响应做 gzip（`gateway/proxy/http.mjs` 的 `shouldCompress`），传输量约为原来的 6%。`text/event-stream`（聊天、搜索进度等流式输出）和 WebSocket 不压缩；小于 1 KB 的响应不压缩。配置文件位置可用 `CLOUDCLI_MULTI_ENV=/path/env` 临时指定（第 7.4 节的测试实例就靠它）。

## 4. 日常运维命令

| 命令 | 作用 |
|---|---|
| `cloudcli-multi start` | 后台启动（`nohup setsid`，退出终端/SSH 不影响）；等待健康检查通过才返回，失败时打印最近日志 |
| `cloudcli-multi stop` | 发 SIGTERM，网关先停所有账号子进程再退出；30 秒未退出会提示 |
| `cloudcli-multi stop --force` | 强制结束网关；遗留的账号子进程下次启动时自动清理 |
| `cloudcli-multi restart` | 停止 + 启动（改配置、手动替换构建产物后用） |
| `cloudcli-multi status` | 网关 pid、运行时长、健康状态、源码分支与提交、Node 版本、各账号子进程 |
| `cloudcli-multi logs [行数]` / `logs -f` | 看 / 跟踪网关日志 `~/.cloudcli-multi/gateway.log` |
| `cloudcli-multi update [--check]` | 改完源码后：按需 `npm ci` → 构建 → 停止服务 → （可选）检查 → 启动。检查不通过仍会启动并提示。见第 7 节 |
| `cloudcli-multi run` | 前台运行（调试用，Ctrl+C 退出） |
| `cloudcli-multi backups` / `restore <名>` | 列出 / 恢复数据备份（恢复前须 `stop`） |
| `cloudcli-multi check` | 隔离检查脚本（见 05）。服务运行中会**先暂停服务**（约 3～5 分钟）、检查完自动恢复：检查项 UPG-09 要求真实数据目录在检查期间不被改动，而运行中的账号子进程会写 `auth.db` |

示例输出：

```
$ cloudcli-multi status
运行中  pid 2854622  已运行 00:03  http://127.0.0.1:3001  健康
源码 /home/vscode/tong/demo/claudecodeui (feat/multi-account@0f7191c)  Node v22.23.4  数据 /home/vscode/.cloudcli-multi
  账号 admin            pid 2854634  端口 33777  运行中
```

## 5. 首次启动与访问

```bash
cloudcli-multi start
```

1. **立即完成初始化**：浏览器打开 `http://127.0.0.1:3001`，会跳到 `/__gw/setup` 创建管理员。在创建之前，任何能访问这个端口的人都能抢先创建管理员；本机的隔离成员和 vscode 共用网络，也能访问 127.0.0.1，所以启动后马上做这一步。
2. 管理员登录后在右下角菜单进入「账号管理」新增普通账号，每个账号指定一个工作目录（规则见 03 第 7.2 节：不能是 home、不能互相包含）。
3. **访问方式**：网关只监听 127.0.0.1，从自己电脑访问用端口转发：
   - VS Code Remote-SSH：「端口」面板转发 3001；
   - 命令行：`ssh -N -L 3001:127.0.0.1:3001 <服务器别名>`，然后打开 `http://localhost:3001`。
4. 要对外直接开放时，前面加 HTTPS 反向代理（nginx/caddy），网关保持 127.0.0.1，并设 `CLOUDCLI_MULTI_TRUST_PROXY=true`。不要直接监听 `0.0.0.0` 走明文 HTTP（启动日志会告警）。

## 6. 开机自启

容器内没有 systemd，**容器/机器重启后网关不会自动起来**，需要执行一次 `cloudcli-multi start`（`start` 是幂等的，已在运行时只提示）。

可选做法（按需选一种）：

| 做法 | 写法 |
|---|---|
| 容器启动命令 | 在容器的启动脚本 / `postStartCommand` 里加 `su - vscode -c '~/.local/bin/cloudcli-multi start'` |
| 登录时补启 | 在 `~/.profile` 末尾加 `~/.local/bin/cloudcli-multi start >/dev/null 2>&1 \|\| true`（每次 SSH 登录检查一次，已运行则跳过） |
| 宿主有 systemd 时 | 写一个 `Type=forking` 的 unit：`ExecStart=…/cloudcli-multi start`、`ExecStop=…/cloudcli-multi stop`、`PIDFile=~/.cloudcli-multi/run/gateway.lock` |

## 7. 修改源码后如何更新（不影响已有功能）

### 7.1 为什么改源码不会“一改就坏”

| 机制 | 效果 |
|---|---|
| 运行的是构建产物（`dist/`、`dist-server/`），不是源码 | 编辑 `src/`、`server/` 时线上不受影响，只有执行 `update` 才生效 |
| `update` 先构建、成功后才重启 | 构建（含类型检查）失败时脚本直接退出，不会重启，正在运行的服务继续用旧产物 |
| 后端构建先写 `dist-server.next/`，成功后再替换 `dist-server/` | 构建中途失败不会留下半套后端 |
| 网关 `gateway/` 是纯 `.mjs`，不经过构建 | 改网关代码后 `restart` 即生效 |
| git 管理全部改动 | 任何一次更新都能用 `git reset` + `update` 回到上一个版本（第 7.5 节） |
| 上游补丁全部带 `cloudcli-multi` 注释，自己的代码在独立目录 | 合并上游时冲突面小，按 05 处理 |

需要知道的一点：前端构建会重写 `dist/`，构建的几十秒内**新打开**的页面可能加载失败（已打开的页面不受影响）。在没人用的时候更新，或者接受这几十秒。

### 7.2 标准更新流程

```bash
cd /home/vscode/tong/demo/claudecodeui
git status                         # 1. 看清楚改了什么
git add -A && git commit -m "…"    # 2. 先提交：留一个可回滚的点
cloudcli-multi update              # 3. 构建 → 重启（依赖变了会先 npm ci）
cloudcli-multi status              # 4. 确认健康，浏览器里点一下改动的功能
```

改动涉及隔离（`server/`、`gateway/proxy`、`isolation.ts`、路径参数）时，用 `cloudcli-multi update --check`，检查全部通过才算完成；不通过时按 05 第 4 节处理。

### 7.3 只改了某一部分

| 改了什么 | 最少操作 |
|---|---|
| `gateway/*.mjs` | `cloudcli-multi restart` |
| `src/`（前端） | `cloudcli-multi update`（也可只 `npm run build:client`，页面刷新即生效，无需重启） |
| `server/`（上游后端） | `cloudcli-multi update`；账号子进程在网关重启时一起重启 |
| `package.json` 依赖 | `cloudcli-multi update`（检测到 lock 文件更新会自动 `npm ci`） |
| 只改配置 env | `cloudcli-multi restart` |

### 7.4 改动大时先在测试实例上验证

另起一个实例：不同端口、不同数据目录，不影响正式服务（两个实例共用 `dist/`，所以只适合验证网关和后端逻辑；验证前端用 `npm run dev`）：

```bash
cat > /tmp/cc-test.env <<'EOF'
CLOUDCLI_MULTI_HOME=/tmp/cc-test-data
CLOUDCLI_MULTI_PORT=39001
CLOUDCLI_MULTI_WORKSPACES=/tmp/cc-test-ws
CLOUDCLI_MULTI_CHILD_MODE=dev     # 子进程直接跑 server/*.ts，不需要构建
EOF
CLOUDCLI_MULTI_ENV=/tmp/cc-test.env cloudcli-multi run      # 前台，Ctrl+C 结束
rm -rf /tmp/cc-test-data /tmp/cc-test-ws                     # 用完删掉
```

### 7.5 回滚

```bash
cd /home/vscode/tong/demo/claudecodeui
git log --oneline -5                 # 找到上一个正常的提交
git reset --hard <提交>              # 或 git revert <坏的提交>
cloudcli-multi update
```

升级导致数据迁移出问题时，再用 `cloudcli-multi stop && cloudcli-multi restore <备份名> && cloudcli-multi start` 恢复数据（备份在版本变化时自动生成，保留 5 份）。

### 7.6 合并上游新版本

按 [05-升级手册](05-升级手册.md)：只合并版本标签，解决冲突后 `cloudcli-multi update --check`。

## 8. 备份

| 内容 | 位置 | 是否需要备份 |
|---|---|---|
| 账号库、签名密钥、各账号索引 | `~/.cloudcli-multi/` | **需要**。网关在版本变化时自动备份到 `backup/`；另外建议定期打包：`cloudcli-multi stop && tar czf cloudcli-multi-$(date +%F).tgz -C ~ .cloudcli-multi && cloudcli-multi start` |
| 会话记录、Claude 登录 | `~/.claude/` | 归 Claude Code 自己管理，按需备份 |
| 代码 | git 仓库 | push 到 `origin` |
| 配置 | `~/.config/cloudcli-multi/env` | 内容少，记录在本文第 3 节即可 |

`secret.key` 丢失会让所有人的登录 Cookie 失效（重新登录即可）；`gateway.db` 丢失会丢掉所有账号，需要从备份恢复。

## 9. 日志与排障

| 日志 | 位置 |
|---|---|
| 网关 | `~/.cloudcli-multi/gateway.log`（`cloudcli-multi logs -f`；超过 10 MB 启动时轮转为 `.1`） |
| 各账号子进程 | `~/.cloudcli-multi/accounts/<账号>/server.log`（5 MB 轮转） |

| 现象 | 先检查 | 处理 |
|---|---|---|
| `start` 报 `NODE_MODULE_VERSION` 不一致 | `cloudcli-multi status` 里的 Node 版本 | 必须是 Node 22；若换过 Node 大版本，执行 `PATH=~/.local/share/cloudcli-multi/node/bin:$PATH npm rebuild` |
| `缺少构建产物 dist/` | 是否从未构建 | `cloudcli-multi update` |
| `another gateway (pid …) is already using` | `cloudcli-multi status` | 已有实例在跑，用它或先 `stop` |
| 端口被占用（`EADDRINUSE`） | `ss -ltnp \| grep 3001` | 换 `CLOUDCLI_MULTI_PORT` 或停掉占用者 |
| 登录后一直显示“正在启动” | 该账号的 `server.log` | 子进程启动失败（1 分钟内失败 3 次会停止重试，下次登录重置） |
| 账号管理页显示“内部用户不一致” | 是否恢复过旧备份 | 点「重建索引」（只丢会话自定义名称、收藏） |
| 页面能开但聊天无响应 | `~/.claude` 登录是否有效 | 在服务器上运行一次 `claude` 确认登录 |
| `stop` 30 秒未退出 | 日志里是否卡在某个账号 | `cloudcli-multi stop --force` |
| 更新后功能异常 | `git log`、`logs` | 第 7.5 节回滚 |

## 10. 卸载

```bash
cloudcli-multi stop
rm ~/.local/bin/cloudcli-multi
rm -rf ~/.config/cloudcli-multi ~/.local/share/cloudcli-multi
rm -rf ~/.cloudcli-multi          # 账号数据，确认不要了再删
```

源码目录和 `~/.claude` 不受影响。
