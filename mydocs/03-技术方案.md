## 1. 设计约束

| # | 约束 | 原因 |
|---|---|---|
| C-1 | 网关代码全部放在 `gateway/`，用 **Node.js ESM 纯 JS**（`.mjs`），不经过上游的 `tsc` 构建 | 不改上游 `tsconfig`、构建脚本 |
| C-2 | **不新增 npm 依赖**，只用上游已有的 `express`、`bcrypt`、`better-sqlite3`、`ws` 和 Node 内置模块；HTTP / WebSocket 转发用 `node:http` + `node:net` 自己实现 | 新增依赖会改 `package.json` 和 `package-lock.json`，每次合并上游都冲突 |
| C-3 | 上游源码只改 `server/shared/isolation.ts`（新文件）+ 15 个调用点；全部由 `CLOUDCLI_ISOLATION_ROOT` 控制 | B-3 |
| C-4 | 子进程就是上游原样的 `node dist-server/server/index.js`，只通过环境变量控制 | 不改上游启动方式 |
| C-5 | 网关只用上游的公开 HTTP 接口（`/api/auth/*`、`/api/providers/sessions/running`、`/api/scheduled-messages`、`/api/user/complete-onboarding`），不直接读上游的数据库 | 上游表结构变化不影响网关 |
| C-6 | 网关自己的路由都在 `/__gw/` 前缀下 | 不与上游路由冲突（上游没有 `/__gw`） |

## 3. 数据设计

### 3.1 数据根目录

默认 `~/.cloudcli-multi/`，用 `CLOUDCLI_MULTI_HOME` 指定。所有文件权限 `600`，目录 `700`。

```
~/.cloudcli-multi/
├─ meta.json                 # { "schema": 1, "upstreamVersion": "1.37.5", "gatewayVersion": "0.1.0" }
├─ gateway.db                # 账号库
├─ secret.key                # Cookie 签名密钥（32 字节随机数，首次启动生成）
├─ accounts/
│  ├─ admin/auth.db          # 子进程 DATABASE_PATH
│  ├─ projA/auth.db
│  └─ projB/auth.db
├─ run/
│  └─ <账号>.json            # { "pid": 12345, "port": 41237, "startedAt": "..." }
└─ backup/
   └─ 20261024-163000/       # 迁移前备份，保留最近 5 份
```

### 3.2 账号库 `gateway.db`

```sql
CREATE TABLE accounts (
  id                 INTEGER PRIMARY KEY,
  username           TEXT NOT NULL UNIQUE,         -- 3–32 位 [A-Za-z0-9_-]
  role               TEXT NOT NULL CHECK (role IN ('admin','member')),
  password_hash      TEXT NOT NULL,                -- bcrypt，cost 12
  password_version   INTEGER NOT NULL DEFAULT 1,   -- 重置密码时 +1，使旧 Cookie 失效
  workspace_root     TEXT NOT NULL,                -- realpath 后的绝对路径；admin 为 home
  note               TEXT,
  internal_password  TEXT NOT NULL,                -- 子进程内部用户的随机密码（32 字节 base64url）
  created_at         TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- PRAGMA user_version = 1
```

- 内部用户名固定为 `cloudcli-internal`。上游是单用户系统（`register` 在已有用户时返回 403），所以每个子进程库中只有这一个用户。
- 内部密码必须以明文保存，因为网关要用它调用上游 `/api/auth/login`。保护手段是文件权限 `600`；这与上游把 JWT 密钥存在 `auth.db` 中属于同一级别。

### 3.3 签名 Cookie（无服务端会话表）

```
gw_session = base64url(JSON{ uid, pv, exp }) + "." + base64url(HMAC-SHA256(secret, payload))
```

- `pv` 等于签发时的 `password_version`；每次请求时比对，不一致就判为失效（ACC-07）。
- `exp` 为签发时间 + 7 天（FR-3.9）。
- 属性：`HttpOnly; SameSite=Lax; Path=/`，请求经 HTTPS 时（`X-Forwarded-Proto: https` 或直连 TLS）加 `Secure`。
- 网关重启后 Cookie 仍然有效，因为签名密钥在 `secret.key` 中持久化。

## 4. 登录与上游 token 衔接

### 4.1 时序

```
浏览器                    网关                                  子进程（projA）
  │  POST /__gw/login        │                                         │
  │ ───────────────────────► │ 限速检查 → bcrypt 校验                   │
  │                          │ ensureRunning(projA) ─── 启动/健康检查 ─► │ GET /api/auth/status
  │ ◄─ 302 / + Set-Cookie ── │                                         │
  │  GET /                   │                                         │
  │ ───────────────────────► │ 校验 Cookie → 转发 ───────────────────► │ 返回 index.html
  │                          │ getUpstreamToken(projA)（有缓存）        │
  │                          │   缓存缺失或剩余 < 1 天 → POST /api/auth/login（内部用户）
  │ ◄─ index.html + 注入脚本 │                                         │
  │  注入脚本执行：                                                      │
  │   若 localStorage['gw-account'] ≠ projA → localStorage.clear()       │
  │   写入 gw-account = projA、auth-token = <token>                      │
  │  上游前端启动，带 token 调用 API / WS ───────────────────────────────► │
```

### 4.2 子进程内部用户初始化

`ensureRunning` 在健康检查通过后调用 `GET /api/auth/status`：

- `needsSetup: true` → `POST /api/auth/register { username: 'cloudcli-internal', password: internal_password }`；
- `needsSetup: false` → 直接 `POST /api/auth/login`；若返回 401（例如账号库被恢复成旧备份），记录错误，在账号管理页显示「内部用户不一致」，提供「重建索引」按钮：删除该账号的 `auth.db` 后重启子进程。会话索引会从 `~/.claude/projects` 自动重建，只会丢失会话自定义名称、收藏这类索引数据。

### 4.3 注入脚本 `inject.js`

转发 `text/html` 响应时，在 `<head>` 后插入：

```html
<script>window.__GW__={account:"projA",role:"member",token:"<上游 token>"}</script>
<script src="/__gw/static/inject.js"></script>
```

`inject.js` 做三件事：

1. **写入 token**：如果 `localStorage['gw-account']` 不等于当前账号，就先执行 `localStorage.clear()`（FR-3.5），再写入 `gw-account` 和 `auth-token`。账号相同时只覆盖 `auth-token`（FR-3.10）。
2. **退出钩子**：包装 `Storage.prototype.removeItem` 和 `clear`。上游前端移除 `auth-token` 时（点击上游的「退出登录」，或 token 过期），跳转到 `/__gw/logout`。网关的退出页清除 Cookie，执行 `localStorage.clear()`，再跳转到登录页。注入脚本自己执行 `clear` 时设一个标志位，不触发跳转。
3. **悬浮菜单**：右下角一个小按钮，显示当前账号；admin 多一个「账号管理」入口；另有「退出登录」。不修改上游 DOM，只追加一个元素。

注入只发生在 HTML 响应上。网关转发 HTML 请求时去掉 `Accept-Encoding`，保证拿到未压缩的内容（上游目前没有启用压缩，这一步是防御性的）。响应头加 `Cache-Control: no-store`，因为页面里带着 token。

### 4.4 限速

在内存中维护两个计数表：`byUsername`、`byIp`。规则：1 分钟窗口内连续失败 5 次就锁定 1 分钟；登录成功后清零该用户名的计数。锁定期间返回 429。参数可用环境变量配置（见第 9 节）。网关重启后计数清零，可以接受。

## 5. 转发

### 5.1 HTTP / SSE（`proxy/http.mjs`）

| 步骤 | 处理 |
|---|---|
| 1 | 路径以 `/__gw/` 开头 → 交给网关路由 |
| 2 | 校验 Cookie；失败时：`Accept` 含 `text/html` 的请求 302 到 `/__gw/login?next=<原路径>`，其他请求返回 401 JSON |
| 3 | **拦截列表**：`POST /api/auth/register`、`POST /api/auth/login` → 403（AUTH-04） |
| 4 | `ensureRunning(account)`；启动中时 HTML 请求返回「正在启动」页（每秒自动刷新），API 请求返回 503 + `Retry-After: 2` |
| 5 | 用 `http.request` 转发到 `127.0.0.1:<port>`：去掉 `Cookie` 中的 `gw_session`，加上 `X-Forwarded-For`、`X-Forwarded-Proto`；`req.pipe(upstreamReq)`、`upstreamRes.pipe(res)`；不设超时（SSE 和长任务需要），客户端断开时销毁上游请求 |
| 6 | `text/html` 响应：缓冲后注入（见 4.3）；其他响应直接流式透传 |
| 7 | 每次请求更新 `account.lastActivityAt` |

### 5.2 WebSocket（`proxy/upgrade.mjs`）

监听 `server.on('upgrade')`：

1. 校验 Cookie，失败时写入 `HTTP/1.1 401 Unauthorized\r\n\r\n` 并销毁 socket（AUTH-01）；
2. `ensureRunning(account)`，等待就绪（最多 30 秒）；
3. `net.connect(port, '127.0.0.1')`，把原始请求行和请求头（去掉 `gw_session`）写给上游，再把已读到的 `head` 写过去，然后双向 `pipe`；
4. 任一端关闭或出错时，两端一起销毁；
5. `account.wsCount` 在连接时加 1、关闭时减 1，用于空闲判断。

需要转发的路径：`/ws`、`/shell`、`/desktop-notifications`、`/plugin-ws/*`。网关不区分路径，全部原样转发。

---

### 5.3 普通账号的全局配置保护（方案 B，`proxy/member-policy.mjs`）

只对 `role = member` 生效，在转发之前判断：

1. 用 `normalizePath()` 规范化路径：URL 解码、合并重复斜杠、去掉末尾斜杠、转小写。这与上游 Express 路由的匹配方式一致（默认不区分大小写、非 strict）；
2. 命中「无条件拦截」表（Skills 增删、插件写操作、系统更新、browser-use 写操作、`POST /api/user/git-config`）时返回 403；
3. MCP 删除：查询参数中任一 `scope` 为 `user` 时拦截；
4. MCP 新增（含 `/mcp/servers/global`）：网关先把请求体读入内存（上限 1 MB），解析出 `scope` 为 `user` 时拦截，否则把读到的内容原样转发（`proxyHttp` 的 `body` 参数）；
5. 返回格式为上游的 `{ success: false, error: { code: 'GATEWAY_MEMBER_FORBIDDEN', message } }`，前端的 `readApiErrorMessage` 能直接显示提示；
6. 普通账号的子进程启动后，网关用内部用户调用 `POST /api/user/complete-onboarding`，跳过上游引导（引导中的 git 步骤会被第 2 条拦截，否则会卡住）。

维护：上游新增会写 home 目录的代码时，检查脚本 UPG-11 会失败（比对 `gateway/check/scenarios/extra.mjs` 中已审核的文件清单），需要复查是否要扩充拦截表。

## 6. 进程管理（`proc/manager.mjs`）

### 6.1 状态机

```
 stopped ──ensureRunning──► starting ──健康检查通过 + 内部用户就绪──► running
    ▲                          │ 30 秒超时 / 进程退出                    │
    │                          ▼                                       │ 空闲回收 / 删除账号 / 网关退出
    │                       failed（1 分钟内失败 3 次，展示错误；        ▼
    └──────────────────────  下一次登录时重置）               stopping ──退出──► stopped
                                                                       │
                              running 期间进程意外退出 ──────────────────┘（下次请求重新启动）
```

同一账号的并发 `ensureRunning` 共用同一个 Promise，保证只启动一次（PROC-03）。

### 6.2 启动参数

```js
spawn(process.execPath, [path.join(APP_ROOT, 'dist-server/server/index.js')], {
  cwd: APP_ROOT,
  env: {
    ...inheritedEnv,                          // 继承用户环境，但删除下表中的变量
    NODE_ENV: 'production',
    HOST: '127.0.0.1',
    SERVER_PORT: String(port),                // 系统分配的随机空闲端口
    DATABASE_PATH: `${HOME}/accounts/${username}/auth.db`,
    WORKSPACES_ROOT: account.workspace_root,
    ...(role === 'member' ? { CLOUDCLI_ISOLATION_ROOT: account.workspace_root } : {}),
  },
  stdio: ['ignore', logFd, logFd],            // 日志写入 accounts/<名称>/server.log，按 5 MB 轮转
});
```

| 从继承环境中删除的变量 | 原因 |
|---|---|
| `JWT_SECRET` | 每个子进程用各自的密钥（FR-3.6） |
| `API_KEY` | 上游会对所有 `/api` 请求校验 `x-api-key`，转发时会失败 |
| `VITE_IS_PLATFORM` | 平台模式会跳过认证 |
| `PORT`、`DATABASE_PATH`、`WORKSPACES_ROOT`、`CLOUDCLI_ISOLATION_ROOT` | 由网关显式设置 |

网关**不主动设置** `CLAUDE_CONFIG_DIR`、`CLAUDE_CODE_OAUTH_TOKEN`，所有子进程使用同一个 Claude 登录（CL-02）。

**随机端口**：先 `listen(0)` 拿到系统分配的端口再关闭，然后传给子进程。如果被其他程序抢先占用，子进程会启动失败，此时换一个端口重试，最多 3 次。

**健康检查**：每 300 ms 请求一次 `GET /api/auth/status`，直到返回 200，最多等 30 秒。

### 6.3 空闲回收

每 60 秒检查一次所有 `running` 的普通账号（admin 跳过，PROC-00）：

```
if wsCount == 0 且 now - lastActivityAt > IDLE_MS:
    running   = GET /api/providers/sessions/running   → data.sessions.length
    scheduled = GET /api/scheduled-messages           → data.length（待执行列表）
    if running == 0 且 scheduled == 0:  stop(account)
```

两个接口都带内部用户的 token 调用。任一接口调用失败时，本轮不回收（宁可多占内存，也不误杀任务）。

**停止**：发送 `SIGTERM`，10 秒后仍未退出就发 `SIGKILL`；然后删除 `run/<账号>.json`。

### 6.4 run 文件与遗留进程（PROC-10、PROC-11）

- 子进程启动成功后写入 `run/<账号>.json`：`{ pid, port, startedAt }`；
- 网关启动时遍历 `run/`：如果 pid 仍然存活，且 `ps -p <pid> -o command=` 中包含 `dist-server/server/index.js`，就先发 `SIGTERM` 再按需发 `SIGKILL`；最后删除文件。检查命令行可以避免 pid 被系统复用后误杀其他进程；
- 网关收到 `SIGINT` / `SIGTERM` 时，并行停止所有子进程，删除 run 文件后退出。

## 7. 账号管理

### 7.1 网关路由

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/__gw/setup` | 无管理员时 | 创建管理员页面；已有管理员时 302 到登录页 |
| POST | `/__gw/api/setup` | 无管理员时 | 创建管理员；已有管理员时返回 409（ACC-02） |
| GET | `/__gw/login` | 公开 | 登录页 |
| POST | `/__gw/api/login` | 公开，限速 | `{ username, password }` → Set-Cookie |
| GET | `/__gw/logout` | 公开 | 清除 Cookie，页面内执行 `localStorage.clear()`，跳转到登录页 |
| GET | `/__gw/api/me` | 已登录 | `{ username, role }` |
| GET | `/__gw/admin` | admin | 账号管理页 |
| GET | `/__gw/api/accounts` | admin | 列表：用户名、工作目录、备注、创建时间、进程状态 |
| POST | `/__gw/api/accounts` | admin | 新增 `{ username, password, workspaceRoot?, note? }` |
| POST | `/__gw/api/accounts/:username/password` | admin | 重置密码 → `password_version + 1` |
| DELETE | `/__gw/api/accounts/:username` | admin | 删除 |
| POST | `/__gw/api/accounts/:username/reindex` | admin | 删除 `auth.db` 并重启子进程（见 4.2） |
| GET | `/__gw/static/*` | 公开 | 静态资源 |

普通账号请求 admin 接口返回 403（ACC-10）。账号接口不提供修改 `workspace_root` 的方法；对这类请求返回 405（ACC-06）。admin 账号本身不能被删除。

### 7.2 工作目录规则（`admin/workspace-rules.mjs`）

```js
const enc = (p) => p.replace(/[^a-zA-Z0-9]/g, '-');   // 与 Claude 的目录编码规则一致

function validateWorkspaceRoot(input, others /* 其他普通账号 */) {
  // 0. 必须是绝对路径；不存在则 mkdir -p；然后 realpath
  // 1. 不在 FORBIDDEN_WORKSPACE_PATHS 之下（从 dist-server/server/shared/utils.js 导入，复用上游列表）
  //    不等于 home，不在 ~/.claude、~/.cloudcli、~/.cloudcli-multi 之下
  // 2. 与任一 other.root：两者都不在对方之下（按路径边界判断）
  // 3. enc(root) 与 enc(other.root)：两者都不以「对方 + '-'」开头，也不相等
  // 5. 如果 root 下存在 .git，返回 warning（不阻止）：「建议把项目放在子目录中」
}
```

默认值为 `<CLOUDCLI_MULTI_WORKSPACES>/<username>`，环境变量未设置时为 `~/workspaces/<username>`。

### 7.3 删除账号

1. `stop(account)`；
2. 删除 `accounts/<名称>/` 和 `run/<名称>.json`；
3. 删除账号库中的记录；

## 8. 上游补丁

### 8.1 新文件 `server/shared/isolation.ts`

> 已实施，最终代码以仓库中的文件为准。与下面草稿的差异：开关改为 `getIsolationRoot()` 每次读取环境变量并按值缓存（单元测试需要切换开关）；`createSession` 被过滤时返回 `''` 而不是 `null`（见 04 清单）。

```ts
import fs from 'node:fs';
import os from 'node:os';
import path from 'node:path';

import { AppError, normalizeProjectPath } from '@/shared/utils.js';

/**
 * Multi-account isolation (cloudcli-multi). When CLOUDCLI_ISOLATION_ROOT is
 * unset every helper here is a no-op and upstream behaviour is unchanged.
 */
const rawRoot = process.env.CLOUDCLI_ISOLATION_ROOT?.trim();
export const ISOLATION_ROOT: string | null = rawRoot
  ? normalizeProjectPath(fs.realpathSync(rawRoot))
  : null;

const CLAUDE_PROJECTS_DIR = path.join(os.homedir(), '.claude', 'projects');

function isUnder(root: string, candidate: string): boolean {
  return candidate === root || candidate.startsWith(root + path.sep);
}

/** Resolves symlinks on the longest existing prefix, so not-yet-created paths still compare correctly. */
function resolveExistingPrefix(candidate: string): string {
  let current = path.resolve(candidate);
  const rest: string[] = [];
  while (!fs.existsSync(current)) {
    const parent = path.dirname(current);
    if (parent === current) break;
    rest.unshift(path.basename(current));
    current = parent;
  }
  return normalizeProjectPath(path.join(fs.realpathSync(current), ...rest));
}

/** Lexical check for paths recorded by providers (session cwd); no filesystem access. */
export function isRecordedPathAllowed(projectPath: string | null | undefined): boolean {
  if (!ISOLATION_ROOT) return true;
  if (!projectPath) return false;
  return isUnder(ISOLATION_ROOT, normalizeProjectPath(path.resolve(projectPath)));
}

/** Symlink-aware check for client-supplied paths. */
export function isRequestedPathAllowed(candidate: string | null | undefined): boolean {
  if (!ISOLATION_ROOT) return true;
  if (!candidate) return false;
  return isUnder(ISOLATION_ROOT, resolveExistingPrefix(candidate));
}

export function assertRequestedPathAllowed(candidate: string | null | undefined): void {
  if (!isRequestedPathAllowed(candidate)) {
    throw new AppError(`Path is outside this account's workspace: ${candidate}`, {
      code: 'ISOLATION_PATH_FORBIDDEN',
      statusCode: 403,
    });
  }
}

/**
 * Post-filter for an already-resolved read-only path: inside the Claude
 * transcripts dir only this account's encoded project dirs stay readable.
 * Other read-only roots (the temp dirs) are left as upstream has them.
 */
export function isReadOnlyPathAllowed(resolvedPath: string | null): boolean {
  if (!ISOLATION_ROOT || !resolvedPath) return true;
  if (!isUnder(CLAUDE_PROJECTS_DIR, resolvedPath)) return true;
  const projectDir = path.relative(CLAUDE_PROJECTS_DIR, resolvedPath).split(path.sep)[0];
  const prefix = ISOLATION_ROOT.replace(/[^a-zA-Z0-9]/g, '-');
  return projectDir === prefix || projectDir.startsWith(prefix + '-');
}
```

> `isolation.ts` 依赖 `utils.ts`（`AppError`、`normalizeProjectPath`），但 `utils.ts` 不反过来依赖 `isolation.ts`，因此没有循环依赖。也是因为这个原因，调用点 3 放在 `file-tree.module.ts`，而不是 `utils.ts`。
>
> `CLAUDE_PROJECTS_DIR` 取 `os.homedir()`，和上游 `READ_ONLY_ROOTS` 的取法一致。在 macOS 上，如果 home 路径中有符号链接，需要对它做 `realpath`，实现时按上游的处理方式对齐。

## 10. 启动、迁移与备份

`cloudcli-multi start` 的流程：

1. 读取配置，创建数据根目录（`700`）；
2. 加锁：`run/gateway.lock` 里写网关 pid，防止同一个数据根目录同时运行两个网关；
3. 清理遗留子进程（6.4）；
4. 读取 `meta.json`。如果 `gatewayVersion`、`upstreamVersion` 与当前版本不同，或网关账号库需要迁移：
   1. 备份到 `backup/<时间>/`（不含 `run/`、`backup/`），只保留最近 5 份（UPG-07）；
   2. 在事务中执行账号库迁移；
   3. **预检**：依次启动每个账号的子进程（上游启动时会自动迁移它自己的 `auth.db`），健康检查通过后停止（admin 除外）；
   4. 任何一步失败：从刚才的备份恢复整个数据根目录，输出失败的账号和日志位置，以非 0 退出（UPG-08）；
   5. 全部成功后更新 `meta.json`；
5. 启动 admin 子进程（常驻）；
6. 开始监听 HTTP 端口。

`cloudcli-multi restore <备份名>`：网关停止时，用指定备份覆盖数据根目录。
