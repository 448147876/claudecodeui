## 1. 背景与目标

使用者是同一个人，同时推进多个大项目。希望**每个大项目对应一个 CloudCLI 账号**：用密码登录某个账号后，只能看到和操作该账号的目录、项目和会话，**在 CloudCLI 的界面和 API 里不能越权**到其他账号；其余功能与上游保持一致。

目标：

1. 一台主机、**共用一次 `claude /login`**；
2. 管理员创建多个普通账号，每个账号绑定一个工作目录；
3. 账号之间**工作目录、项目、Session 三方面隔离**，界面和 API 均不可越权；
4. 所有账号通过**同一个地址和端口**访问；
5. **最小改动**：上游改动集中、受开关控制；重装升级不丢数据，方便合并上游新版本；
6. 只有一个 Claude 登录，不改 Claude CLI / SDK 的调用方式。

### 1.1 隔离边界（v4 明确）

| 层面 | 是否隔离 | 说明 |
|---|---|---|
| CloudCLI 界面与 HTTP / WebSocket API | **隔离** | 文件浏览、项目、会话、搜索、聊天、命令、Agent API 等都不能访问其他账号的目录和数据 |
| 网页终端 | 不隔离 | 照常可用，可以 `cd` 到任何目录（上游原样） |
| Claude 自身的工具（Bash、Read、Write 等） | 不隔离 | Claude 在本账号目录启动，但它的工具能访问系统用户可访问的一切 |
| 操作系统 | 不隔离 | 所有进程同一个系统用户 |

> 这是「应用层隔离」：防止在界面上误操作、误看到别的项目，不防止有意通过终端或让 Claude 去读其他目录。

## 2. 功能需求

### FR-1 账号管理

| 角色 | 产生方式 | 说明 |
|---|---|---|
| 管理员 | 首次打开页面时创建，只有一个 | 可进入账号管理页；自己也能正常使用，工作目录为整个 home，**不开隔离开关**，体验与上游一致 |
| 普通账号 | 管理员新增 | 对应一个大项目；工作目录固定；开启隔离开关 |

账号管理页面做到**最简**：

- **列表**：用户名、工作目录、备注、创建时间、进程状态（运行中 / 未启动）
- **新增**：用户名（唯一，3–32 位字母数字 `-_`）、密码（≥6 位）、工作目录（绝对路径，不存在则创建）、备注（可选）
- **重置密码**：重置后该账号已登录的浏览器会话立即失效
- **删除**：停止该账号进程，删除其索引数据（数据库、临时文件）；**工作目录和 Claude 对话记录一律保留**
- 工作目录创建后不可修改（会话和项目绑定在路径上）；要换目录就删了重建

工作目录规则：

1. 不能是系统目录（复用上游 `FORBIDDEN_WORKSPACE_PATHS`），也不能是 home 本身或 `~/.claude`、`~/.cloudcli-multi` 等数据目录
2. 不同普通账号的目录**不能相互包含**（`/w/a` 与 `/w/a/sub`）
3. 不同普通账号的目录按 Claude 规则编码后（非字母数字字符替换为 `-`，如 `/w/a` → `-w-a`）**不能互为前缀**（`/w/a` 与 `/w/a-2`、`/w/a_2`）。v4 说明：会话过滤按 `cwd` 判断，并不依赖这一条；保留它是为了 FR-2 (e) 能按编码前缀收窄只读目录
4. 新增时默认填 `<总目录>/<用户名>`，可改
5. **建议**：项目放在账号目录的子目录里（`/w/projA/repo1`），不要把账号目录本身当作 git 仓库，见第 6 节第 7 条；新增账号时若目标目录已是 git 仓库则给出提示

### FR-2 任务隔离（普通账号）

隔离开关：环境变量 `CLOUDCLI_ISOLATION_ROOT=<账号工作目录>`（名称以技术方案为准）。未设置时所有逻辑与上游完全一致。路径判断统一为：先 `realpath`，再判断 `p === root || p.startsWith(root + '/')`。

| 编号 | 隔离项 | 要求 | 实现位置 |
|---|---|---|---|
| (a) | 工作目录 | 文件浏览、目录选择、新建文件夹、新建项目、克隆项目都限定在本账号目录内 | 上游已有 `WORKSPACES_ROOT` + `validateWorkspacePath`，无需改代码 |
| (b) | 项目 | 项目列表只显示本账号目录下的项目；任何入口都不能登记本账号目录外的项目 | 每账号独立 `DATABASE_PATH` + 上游补丁：`projectsDb.createProjectPath` 拒绝目录外路径 |
| (c) | Session | 会话列表、搜索只显示 `cwd` 在本账号目录下的会话；系统终端里在该目录下开的会话也归入该账号 | 上游补丁：`sessionsDb.createSession` 对目录外会话跳过入库（四个 provider 的同步器都经过这里） |
| (d) | 新建会话 / Agent API | `POST /api/providers/sessions`、`POST /api/agent` 传入目录外的 `projectPath` 时拒绝；隔离模式下 Agent API 必须指定 `projectPath`（上游默认克隆到 `~/.claude/external-projects`，在账号目录外；而上游的自动清理只认那个目录，所以不改默认位置，直接要求显式指定） | 新建会话由 (b) 覆盖；Agent API 先克隆后登记，需在入口单独校验 |
| (e) | 只读目录 | 文件查看器的只读目录中，`~/.claude/projects` 收窄为「编码名以本账号编码前缀开头的子目录」；`/tmp` 收窄为本账号的 Claude 任务输出（v4.4，见 (j)） | 上游补丁：`file-tree.module.ts` 中只读路径解析的结果过滤 |
| (f) | 聊天工作目录 | 聊天 WebSocket 中客户端传入的 `options.cwd` 必须在本账号目录内，否则使用会话自身的 `project_path` | 上游补丁：`chat-websocket.service.ts` 的 `cwd` 取值处 |
| (g) | 斜杠命令 | `/api/commands` 中的 `projectPath`（读取 `CLAUDE.md`、`.claude/commands`）必须在本账号目录内 | 上游补丁：`commands.routes.ts` 读取 `projectPath` 处 |
| (h) | MCP / Skills | `/api/providers/:provider/mcp/servers*`、`/api/providers/:provider/skills*` 中显式传入的 `workspacePath` 必须在本账号目录内；未传时保持上游默认 | 上游补丁：MCP、Skills 两个 provider 基类中的 `resolveWorkspacePath` |

已核对、**无需改动**的入口：git、worktrees、taskmaster、file-tree 项目文件接口都按 `projectId` 从本账号数据库查路径；聊天按 `sessionId` 从本账号数据库查会话。只要 (b)(c) 成立，这些入口天然隔离。完整的路径参数审核结果见 `04-上游文件改动清单.md`。

### FR-2 (j) 间接越界入口的加固（v4.4，独立测试发现）

这几处不是直接接收路径参数，而是通过文件名、仓库配置、克隆地址、共用临时目录间接越界。全部由 `CLOUDCLI_ISOLATION_ROOT` 控制，开关关闭时与上游一致：

| 入口 | 问题 | 处理 |
|---|---|---|
| 文件接口写 `.git` | git 会执行 `.git/config` 里的 `core.fsmonitor`、`.git/hooks` 里的脚本。普通账号先在自己项目里写入这些文件，再让 git 运行，就能以共用的系统用户身份执行命令，绕过全部目录限制 | ① 文件接口（保存、新建、重命名、删除、上传、读取）拒绝访问 `.git` 内的任何路径（补丁 #9）；② 网关给普通账号的进程设置 `GIT_CONFIG_*` 环境变量，强制 `core.fsmonitor=false`（环境变量优先于仓库配置），即使配置是从终端写进去的也不执行 |
| Taskmaster 文档名 | `fileName` 直接拼进路径，`../` 可以读写自己目录以外的文件 | 三个读取 `fileName` 的路由要求它是不带目录的文件名，否则 400（补丁 #10） |
| 克隆项目 | 克隆来源可以填本机路径或 `file://`，把本机任意 git 仓库复制进自己的目录 | 只接受 http(s)、ssh、git 地址和 `user@host:path`（补丁 #11） |
| `/tmp` 只读范围 | 文件查看器把 `/tmp` 当作只读目录，可以列出并读取其中所有文件，包括其他账号的任务输出 | 只放行 `<tmp>/claude-<uid>/<本账号目录编码>/…`（Claude 后台任务输出的位置）；`/tmp` 本身不能列出 |
| 项目内的符号链接 | 文件接口只比较路径字符串，不解析符号链接。项目里的链接（克隆来的仓库可以带有）指向 `.git` 或其他账号的目录时，既能绕过上面对 `.git` 的限制，也能跨账号读写删文件 | 文件接口在判断前先解析符号链接：指向项目外或 `.git` 的链接一律拒绝，包括读取；指向项目内部的链接照常工作。要删除这类链接请用终端（补丁 #9） |
| 命令文件、Taskmaster 文档与任务文件 | 这些读取点各自只做字符串比较，项目里（克隆来的仓库可以带有）的符号链接指向其他账号的文件时，文件内容会被当作命令内容、文档或任务读出来（独立复测发现 `commands/execute`，随后排查出同类读取点） | 读取前先解析符号链接，指向工作区外的拒绝（补丁 #13、#15）。命令列表不需要处理：上游扫描目录时符号链接本来就被跳过 |
| git 的文件参数 | `resolveRepositoryFilePath` 调用校验函数时没有传入根目录，实际只检查了空字节；目前靠 git 自身拒绝工作区外的路径才没有泄露 | 隔离模式下每个候选路径都必须在本账号工作区内（补丁 #14） |
| worktree 创建 | 账号目录本身是仓库时，git 会先在工作区外建出 worktree 目录，之后才因登记项目失败而回滚，留下空目录 | 创建前先校验目标目录，工作区外直接拒绝，不留任何东西（补丁 #12） |
| MCP、Skills 默认目录 | 没有指定 `workspacePath` 时用进程的当前目录，即共用的安装目录；普通账号可以往里写 `.mcp.json` | 默认改为本账号目录（补丁 #7、#8 的扩展） |

代价：普通账号在文件查看器里不能打开 `.git` 目录内的文件，也不能通过文件接口读写或删除指向项目外的符号链接（用终端处理）；git 的提交、分支、状态等功能不受影响。

### FR-2 (i) 全局配置保护（方案 B，v4.3）

普通账号**不能通过界面或 API 修改所有账号共用的配置**；管理员不受限制。由网关拦截，不改上游。被拦截的请求返回 403，提示「普通账号不能修改全局配置：…，请使用管理员账号操作」。

| 共用配置 | 被拦截的操作（仅普通账号） | 仍然允许 |
|---|---|---|
| 用户级 MCP（`~/.claude.json` 顶层、各 provider 的用户级配置） | `scope=user` 的新增、删除；`/mcp/servers/global` 的 `scope=user` | 项目级、local 级（只能写本账号目录）；查看列表 |
| 用户级 Skills（`~/.claude/skills` 等） | 新增、删除 | 查看列表 |
| 插件（`~/.claude-code-ui`） | 安装、启用/停用、更新、卸载 | 查看、使用已安装的插件 |
| 安装目录 | 系统更新 | — |
| browser-use（`~/.cloudcli/browser-use`） | 修改设置、安装运行时 | 查看设置、使用 |
| 全局 git 配置（`~/.gitconfig`） | 保存 git 用户名和邮箱 | 查看 |

- 路径按上游路由的匹配方式规范化后再判断（不区分大小写、忽略多余或末尾的斜杠、URL 解码、重复参数任一为 `user` 即拦截），防止换个写法绕过；
- 普通账号的进程首次启动时，网关自动完成上游的首次引导，因为引导中的 git 步骤会写全局 git 配置；普通账号沿用管理员设置的 git 身份；
- 前端界面上的这些按钮仍然显示，点击后出现上述提示；
- **不在保护范围内**：网页终端和 Claude 自身的工具仍能修改这些文件（见 1.1 和第 7 节）。

**不做隔离的部分**（使用者是同一个人）：

- 网页终端照常可用（终端 WebSocket 的 `projectPath` 只决定初始目录）
- Claude 跳过权限确认、项目级 MCP 等**保持上游原样**；插件、用户级 MCP/Skills、browser-use、系统更新仅管理员可改（FR-2 (i)）
- 聊天上传的附件仍存在共用的 `~/.cloudcli/assets`（文件名随机，互不冲突）
- 插件目录共用（`~/.claude-code-ui`），每个账号的进程各自运行一份；见第 6 节

### FR-3 登录与入口

1. 所有账号访问同一个地址，例如 `http://host:3001/`，无路径后缀
2. 未登录访问任何页面跳到网关登录页；未登录的 API 请求返回 401，WebSocket 握手被拒绝
3. 有「退出登录」入口；退出时清除网关 Cookie、浏览器 `localStorage`（含上游的 `auth-token`、草稿、输入历史）
4. 管理员在界面里能进入账号管理；普通账号看不到入口，直接请求账号管理 API 返回 403
5. 同一浏览器同一时间只登录一个账号；登录新账号时，中转页先清空 localStorage 再写入新 token，不残留上一个账号的草稿
6. **与上游登录的衔接（v4 新增）**：
   - 每个子进程保留上游自己的 JWT 登录，**各自独立的 JWT 密钥**（上游默认行为，不设 `JWT_SECRET`）；
   - 子进程首次启动时，网关通过上游 `POST /api/auth/register` 创建一个内部用户（随机密码，保存在账号库）；
   - 用户在网关登录成功后，网关用内部用户调用子进程 `POST /api/auth/login` 换取 token，通过一个中转页写入 `localStorage['auth-token']` 再进入主界面，用户**不会看到上游登录页**；
   - 网关拦截子进程的 `/api/auth/register`、`/api/auth/login`，不对浏览器开放；
   - 因为密钥不同，A 账号的 token 拿到 B 账号的进程上一律无效；
   - 不使用 `VITE_IS_PLATFORM`（它在前端构建时生效，会改变 40 多处界面行为）。
7. 网关按 Cookie 转发 HTTP、SSE（`?token=`）和 WebSocket upgrade（聊天、终端）
8. **登录限速（v4.1）**：同一用户名或同一 IP 连续失败 5 次，锁定 1 分钟（次数、时长可配置）；锁定期间返回 429，正确密码也不放行
9. **Cookie 安全属性（v4.1）**：`HttpOnly`、`SameSite=Lax`；经 HTTPS 访问时加 `Secure`；有效期 7 天，不超过上游 token 的有效期（7 天）
10. **token 刷新（v4.1）**：每次经过中转页（登录、打开首页）时，网关都向子进程换取新 token 写入 localStorage，避免网关 Cookie 有效而上游 token 已过期
11. **监听地址（v4.1）**：网关默认只监听 `127.0.0.1:3001`，可用环境变量改为 `0.0.0.0`；需要远程访问时推荐经 HTTPS 反向代理或 SSH 隧道，启动日志中对 `0.0.0.0` 且非 HTTPS 的情况给出警告

## 3. 「对 Anthropic 仍是一个人」的要求

| 要求 | 说明 |
|---|---|
| 只有一个 Claude 登录 | 所有账号的进程都读同一个 `~/.claude`；**不**使用 `CLAUDE_CONFIG_DIR`、`CLAUDE_CODE_OAUTH_TOKEN` 等方式分开登录；不创建第二个 Claude 账号 |
| 不改 Claude CLI 和 SDK 的调用方式 | 上游通过官方 `@anthropic-ai/claude-agent-sdk` 调用，本改造不触碰这部分 |
| 仅限本人使用 | 个人订阅不得多人共用。若以后要给其他人使用，必须改为每人自己的 Claude 凭据（另立需求） |
| 用量仍受单个订阅限制 | 多个账号并行跑任务会更快碰到用量上限；避免 24 小时无人值守的高并发 |

## 6. 方案方向与约束

```
浏览器 ──► 统一入口 :3001（新增，gateway/：登录页、账号管理、按 Cookie 转发 HTTP/SSE/WS、按需启动进程）
             ├─ admin 的 CloudCLI 进程   WORKSPACES_ROOT=~         （无隔离开关）
             ├─ projA 的 CloudCLI 进程   WORKSPACES_ROOT=/w/projA  CLOUDCLI_ISOLATION_ROOT=/w/projA  DATABASE_PATH=~/.cloudcli-multi/projA/auth.db
             └─ projB 的 CloudCLI 进程   WORKSPACES_ROOT=/w/projB  CLOUDCLI_ISOLATION_ROOT=/w/projB  DATABASE_PATH=~/.cloudcli-multi/projB/auth.db
                        ▲ 全部监听 127.0.0.1 的随机端口，同一个系统用户，共用 ~/.claude
```

1. **为什么是一个账号一个进程**：CloudCLI 的数据库、会话索引、路径校验都是「每个进程一份」，而且 `WORKSPACES_ROOT`、`DATABASE_PATH`、`SERVER_PORT`、`HOST` 都是上游支持的环境变量。改成真正的多租户要动几十个文件，无法跟进上游。
2. **进程按需启动、空闲回收**：
   - 普通账号登录时启动，健康检查（上游 `GET /api/auth/status`）通过后再转发；**admin 进程随网关启动并常驻（v4.1）**；
   - 同时满足以下条件超过 30 分钟（可配置）才回收：无浏览器连接、无运行中的 Claude 任务、无待执行的定时消息；
   - **空闲判断只用上游已有接口（v4.1）**：运行中任务用 `GET /api/providers/sessions/running`，定时消息用 `GET /api/scheduled-messages`（无 `sessionId` 时返回待执行列表），网关用内部用户的 token 调用，不新增上游改动；
   - 每个在线账号约 150–300 MB；子进程异常退出时，下次请求自动重启。
3. **端口与进程文件（v4.1）**：子进程使用系统分配的随机空闲端口；端口和 PID 写入 `<数据根目录>/run/<账号>.json`（权限 `600`）。网关启动时读取这些文件，清理上次遗留的子进程；网关正常退出时停止所有子进程并删除这些文件。
4. **应用层隔离**：见 1.1；终端和 Claude 工具不隔离。
5. **插件端口**：插件后端自己选端口，固定端口的插件在两个账号同时在线时会冲突，表现为第二个账号里该插件不可用。属已知限制，不在本次处理。
6. **浏览器本地数据**：草稿、输入历史存在 localStorage，退出登录和登录新账号时都会清空。
7. **worktree**：上游把 worktree 建在仓库的同级目录（`<repo>-worktrees/`）。如果账号目录本身就是仓库，目标会落在账号目录外，v4.4 起在创建之前就被拒绝（不再留下目录）。因此仍要求项目放在账号目录的子目录里，网关新增账号时若目标目录已是 git 仓库则给出提示。
8. **AGPL-3.0**：若把改造后的程序通过网络提供给他人使用，需向其提供源码；单人自用不涉及。

## 7. 风险与应对

| 级别 | 风险 | 应对 |
|---|---|---|
| 高 | 终端和 Claude 工具能访问其他账号的目录（同一系统用户） | 已接受（见 1.1）。如需降低误操作，可在普通账号目录的 `.claude/settings.json` 中用 `permissions.deny` 禁止读取其他账号目录；该配置由使用者自行维护，网关不自动写入 |
| 高 | 上游新增接受原始路径参数的接口，隔离失效 | B-5 静态扫描 + API 越权场景回归 |
| 高 | **普通账号可以通过网页终端或 Claude 工具读写网关数据** `~/.cloudcli-multi`（`gateway.db`、`secret.key`），借此把自己改成管理员或伪造任意账号的登录态（GLB-04，已实测） | 应用层无法阻止；只有把各账号的进程放到不同的系统用户下（系统用户级隔离）才能解决 |
| 中 | 应用界面中有作用于全局的功能：用户级 MCP、用户级 Skills、插件、系统更新、browser-use、全局 git 配置 | **已处理（方案 B，FR-2 (i)）**：网关对普通账号拦截，POL-01～05 验证；上游新增引用 home 目录的代码时 UPG-11 会提醒复查 |
| 中 | Claude CLI 运行时会改写 `~/.claude.json`，可能覆盖同一时刻在界面上保存的用户级或 local 级 MCP（已实测，见 03 T-7） | Claude CLI 本身的行为，无法在网关层解决；保存后刷新列表确认 |
| 低 | 附件目录 `~/.cloudcli/assets` 是共用的，知道文件名就能读到其他账号上传的附件（GLB-06）；文件名随机，不会被列出 | 接受 |
| 中 | 本机可直连子进程端口，绕过网关 | 子进程只监听 `127.0.0.1`；属同一系统用户的边界，接受 |
| 低 | 账号目录本身是 git 仓库时，worktree 无法创建 | 创建前被拒绝，不留残留；项目放在子目录即可（见 6.7） |
| 中 | 多进程内存与启动扫描开销 | 空闲回收；控制同时在线账号数 |
| 中 | 固定端口插件在多账号同时在线时冲突 | 已知限制 |
| 中 | 单订阅用量上限 | 避免长时间无人值守的高并发 |
| 低 | 网关 Cookie 与上游 token 有效期不一致 | FR-3.9、FR-3.10 |
| 低 | 上游补丁与上游改动冲突 | 逻辑集中在 `isolation.ts`，调用点 1～3 行 |

## 8. 验收标准

以 admin、projA（`/w/projA`）、projB（`/w/projB`）为例；逐条场景见 `06-BDD验收场景.md`。

**账号管理**
- [ ] 首次启动显示「创建管理员」页面；创建后不能再访问
- [ ] 只有 admin 能打开账号管理页和调用账号管理 API；能新增 projA、projB
- [ ] 新增目录为系统目录、互相包含或编码后互为前缀的账号时被拒绝并提示
- [ ] 重置 projA 密码后旧密码失效，已登录的浏览器被要求重新登录
- [ ] 删除 projB 后进程停止，`/w/projB` 和 `~/.claude/projects` 下的对话记录仍在

**隔离（应用层）**
- [ ] projA 的项目列表、会话列表、搜索里没有 projB 和 admin 的内容
- [ ] projA 的文件浏览和目录选择出不了 `/w/projA`；只读目录中只能看到 projA 自己的对话记录目录
- [ ] 用 projA 的登录态构造请求（新建会话、Agent API、聊天 `cwd`、斜杠命令、MCP、Skills）指向 `/w/projB` 时全部被拒绝或忽略
- [ ] projA 的 token 在 projB 的进程上无效
- [ ] 在系统终端里 `cd /w/projA/x && claude` 开的会话，只出现在 projA 的列表里
- [ ] admin 能看到全机会话，体验与上游一致

**入口与升级**
- [ ] 所有账号用同一地址端口访问，无后缀；登录后不出现上游登录页；退出登录或切换账号后 localStorage 被清空
- [ ] 连续 5 次密码错误后被锁定 1 分钟；Cookie 带 `HttpOnly`、`SameSite=Lax`
- [ ] 网关默认只监听 `127.0.0.1`
- [ ] admin 进程随网关常驻；网关异常退出后重启，不残留旧的子进程
- [ ] 有运行中任务或待执行定时消息的账号不会被空闲回收
- [ ] 删除安装目录重新安装并启动后，账号与会话原样恢复
- [ ] 数据库迁移前生成备份，最多保留 5 份
- [ ] 全程只有一个 Claude 登录，任何账号都不需要再执行 `claude /login`
- [ ] 不设置隔离开关时，上游自带测试全部通过
